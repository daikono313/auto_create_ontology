# 0009. ユーザージャーニーと状態遷移をオントロジーに加える

- ステータス: 承認
- 日付: 2026-10-23

## コンテキスト

これまでのスキーマ（ADR 0005）は、Object・Property・Link・Action を一覧で持つだけだった。
Action を実行する順番（ログイン → 商品を見る → カートに入れる → 購入する）や、
Action によって Object の状態がどう変わるか（Basket が「商品あり」から「注文済み」になる）は表せなかった。

また、クローラーはリンクを辿るだけで、ログインやフォーム送信をしない。
books.toscrape.com では、カートより先（購入・購入完了）のページを一度も取得しておらず、Order が出力されなかった。

## 決定

スキーマに次の2つを加える（`ontogen/schema.py`）。

- `journeys`: ユーザーが目的を達成するまでの流れ。ステップごとに、実行する Action、作成・更新する Object、
  対応する GA4 のイベント名（ADR 0010）を持つ。
  サイト上で確認できたステップは `observed: true`、ECの典型的な流れから補ったステップは `observed: false` にする。
- `state_machines`: 状態を持つ Object（Basket、Order など）が取りうる状態と、どの Action でどの状態に移るか。

確認できなかったステップや状態は、根拠のない推測として隠さず、`observed: false` と `open_questions` で明示する。
ジャーニーの組み立てに必要な Action や Object がサイトから見つからない場合は、【推定】として Object・Action にも加える。

画面（`viewer.html`）とレポートでは、ジャーニーをフローチャート、状態遷移を状態遷移図で表示する。

## 検討した代替案

- Playwright でログインから購入直前まで実際に操作して確かめる: 精度は上がるが、テスト用アカウントと、
  規約上の扱い、実際に注文しないための安全策が必要になる。今回は見送り、推定したステップの検証方法として後で検討する
- ジャーニーを Action の `description` に文章で書く: 順序や状態を機械的に扱えず、図にもできない

## 結果

- サイトから見えない購入以降の流れも、【推定】と明示したうえで叩き台に含められる。
- スキーマが変わるため、LLM キャッシュは無効になる。gold と評価（ADR 0008）はジャーニーと状態遷移をまだ採点しない。
- ジャーニーを補うと、購入まわりの推定の Object・Action が増え、gold との比較で適合率が下がる
  （books.toscrape.com で Action の適合率が 0.06 になった）。そこで評価では、推定の要素（根拠がない、または説明が【推定】で始まる）が
  gold のどの要素とも一致しなかった場合は適合率の分母から外し、`inferred` として件数だけ出すことにした。
- 推定したステップが増えるほど、レビューで確認する量も増える。ヒアリング事項とあわせて確認する前提になる。
