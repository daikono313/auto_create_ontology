# 0006. URLパターン単位の2段階生成

- ステータス: 承認
- 日付: 2026-10-23

## コンテキスト

ECサイトは商品ページが数千あっても、テンプレートは数種類しかない。すべてのページをLLMに渡すのは無駄で、
一度に渡せる量も超える。一方で、1回の呼び出しでサイト全体を扱うと、ページ種別ごとの細かい項目が出力から漏れやすい。

## 決定

- 代表ページを選ぶ。URLパスのうち数字を含むセグメントを `*` に置き換えたものを「パターン」とみなす
  （`crawl.url_pattern`）。パターンごとに最大 `--per-pattern`（既定3）件だけ取得する。
- ページを要約する。HTML 全体ではなく、見出し・パンくず・表・フォーム・JSON-LD・itemprop・class 属性・
  画像の alt 属性・リンクテキスト・本文の先頭を抜き出して渡す（`extract.digest`）。
  class 属性を含めているのは、星評価のように値が class 属性にしか入っていないことがあるため。
- 2段階で生成する。
  1. パターンごとに概念候補を抽出する（並列実行）
  2. すべての候補とサイトマップ（パターン一覧）を渡して統合・名寄せする

## 検討した代替案

- 全ページを1回で渡す: 規模が大きいサイトでは成り立たない
- ページごとに抽出して統合する: 同じテンプレートで同じ結果が重複し、呼び出し回数が無駄に増える
- DOM 構造でテンプレートを判定する: 精度は上がるが実装の手間が大きい。URL パターンで足りなくなったら検討する

## 結果

- 呼び出し回数がページ数ではなくパターン数に比例する。
- URL にIDが入らないサイト（クエリパラメータでページを切り替えるURL、スラッグだけのURL）では、同じテンプレートのページが別々のパターンになる。
  Shopify 系（`/products/<slug>`）はスラッグのみなので、検証時に対応が必要になる見込み。
- パターンごとの上限に達したページは取得しないので、そのページにあるリンクも辿らない。深い階層にしかないページ種別を見落とす可能性がある。
