# 0008. 人手の正解データで定量評価する

- ステータス: 承認
- 日付: 2026-10-23

## コンテキスト

「良いオントロジー」の正解は一つではなく、粒度・命名・エンティティか属性かで揺れる。
それでも評価軸がないと、プロンプトや前処理を変えたときに良くなったのか悪くなったのか判断できない。

## 決定

- サイトごとに人手で正解（`gold/<site>.yaml`）を作る。
- 正解の書き方:
  - 名前は `|` 区切りで別名を列挙する（例: `Basket|Cart|ShoppingCart`）。照合は正規化したうえでの完全一致、または類似度 0.85 以上
  - サイトから読み取れるか微妙な要素は `optional: true`（プロパティは先頭に `?`）にする。
    生成されても適合率に影響せず、生成されなくても再現率に影響しない
  - `properties` を書いていない Object は、プロパティを採点しない
  - Link は向きを問わず、両端の Object の組み合わせで比較する
- Object / Property / Link / Action ごとに、適合率・再現率・不足（missing）・余分（extra）を出す（`ontogen eval`）。

## 検討した代替案

- LLM-as-judge で評価する: 柔軟だが、評価の結果も実行ごとに変わるので、改善の比較に使いにくい。補助として将来追加を検討する
- 人の目視だけで評価する: 変更のたびに行うには手間が大きい

## 結果

- 改善の効果を数値で比べられるようになる。
- 正解の作り方しだいで数値が大きく動く（初回、`currency` などの妥当な推定を正解に入れていなかったため、プロパティの適合率が 0.52 になった）。
  余分（extra）に出た要素は、生成の誤りか正解の漏れかを毎回判断する必要がある。
- LLM の出力は実行ごとに揺れるため、比較には複数回の実行が必要になる。
- `open_questions` の質は評価していない。
